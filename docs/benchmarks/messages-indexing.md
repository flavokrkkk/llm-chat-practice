## Исследование производительности индексов в PostgreSQL (3M+ строк)

В рамках проекта было проведено практическое исследование влияния различных
типов индексов на производительность запроса получения последних сообщений чата:

Запрос: SELECT id, chat_id, role, content, idempotency_key, created_at FROM
messages WHERE chat_id = '0013b0b5-2d69-441f-b6c1-1c2d30215a02' ORDER BY
created_at DESC LIMIT 50;

Тестовый стенд:

- СУБД: PostgreSQL 16 (в Docker-контейнере)
- Объем таблицы messages: ~3 000 000 строк (сгенерировано через
  generate_series)
- Инструмент анализа: EXPLAIN (ANALYZE, BUFFERS)

1. Сценарий: Без индексов (Baseline)

Индексы по полям chat_id и created_at отсутствуют.

- Execution Time: ~2024.66 ms (~2.02 секунды)
- План выполнения: Parallel Seq Scan (2 воркера) + Sort (quicksort)
- I/O Буферы: shared hit=14141 read=60680 (~485 МБ прочитано с диска)

Вывод:

База выполнила полное последовательное сканирование всей таблицы на 3 миллиона
строк. На каждый запрос тратится более 2 секунд процессорного времени и читается
полгигабайта данных. При конкурентной нагрузке сервер моментально уйдет в 100%
CPU и исчерпает I/O лимиты.

2. Сценарий: Одиночный индекс по (chat_id)

DDL: CREATE INDEX idx_messages_chat_id ON messages(chat_id);

- Execution Time: ~0.73 ms (ускорение в ~2770 раз по сравнению с baseline)
- План выполнения: Bitmap Index Scan + Sort (quicksort)
- I/O Буферы: shared hit=64 read=3

Вывод:

Поиск строк конкретного чата происходит за доли миллисекунды по B-Tree индексу.
Однако в плане присутствует узел Sort: база находит неупорядоченные строки и
затем сортирует их в оперативной памяти (RAM). Для маленьких чатов это
незаметно, но в больших каналах/чатах на сотни тысяч сообщений сортировка в
памяти создаст серьезную нагрузку на CPU.

3. Сценарий: Одиночный индекс по (created_at DESC)

DDL: CREATE INDEX idx_messages_created_at ON messages(created_at DESC);

- Execution Time: ~194.70 ms
- План выполнения: Parallel Seq Scan (индекс проигнорирован планировщиком)
- I/O Буферы: shared hit=14329 read=60492

Вывод:

Планировщик запросов посчитал использование индекса по дате неэффективным, так
как для фильтрации по chat_id все равно пришлось бы перебирать гигантский объем
записей. СУБД вернулась к Parallel Seq Scan. Одиночный индекс по полю сортировки
бесполезен, если в запросе есть селективный фильтр WHERE по другому полю.

4. Сценарий: Составной индекс (Composite) (chat_id, created_at DESC)

DDL: CREATE INDEX idx_messages_chat_created ON messages(chat_id, created_at
DESC);

- Execution Time: ~0.63 ms (на прогретом кэше: <= 0.1 ms)
- План выполнения: Index Scan
- I/O Буферы: shared hit=50 read=4

Вывод (Best Practice):

Идеальный план выполнения:

1.  Узел Sort полностью отсутствует: данные в B-Tree индексе физически
    сгруппированы по chat_id и уже отсортированы по created_at DESC.
2.  База данных выполняет точечный Index Scan, считывая ровно требуемые 50
    записей прямо из индекса без накладных расходов на сортировку в памяти.

Итоговое сравнение

| Индекс                         | Execution Time | Основной узел плана       | Наличие сортировки в RAM     |
| :----------------------------- | :------------- | :------------------------ | :--------------------------- |
| **Нет индексов**               | 2024.6 ms      | Parallel Seq Scan         | Да                           |
| **(chat_id)**                  | 0.73 ms        | Bitmap Index Scan         | Да (Sort: quicksort)         |
| **(created_at DESC)**          | 194.7 ms       | Parallel Seq Scan (игнор) | Да                           |
| **(chat_id, created_at DESC)** | **0.63 ms**    | **Index Scan**            | **Нет (Zero Sort Overhead)** |

Архитектурное правило (Rule of Thumb):

Для запросов вида WHERE column_a = :val ORDER BY column_b LIMIT :n составной
индекс должен строиться строго в порядке:
CREATE INDEX ON table (column_a, column_b [DESC]);
(Сначала колонки точного равенства, затем колонка диапазона / сортировки —
правило левого префикса).
