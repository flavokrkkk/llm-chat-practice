# ТЗ: LLM Chat Backend — практика по PostgreSQL

Oct 23, 2026 · @Ivan

## Цель

Собрать бэкенд чата с LLM на FastAPI и сыром SQL так, чтобы каждое задание закрывало вопрос из вакансии: индексы, оптимизацию запросов и транзакции в PostgreSQL. LLM не нужна: ответ ассистента можно имитировать заглушкой с `asyncio.sleep`.

| Тема собеса                                                 | Где закрывается |
| ----------------------------------------------------------- | --------------- |
| Индексы: B-tree, составные, функциональные, частичные       | Задание 2       |
| EXPLAIN ANALYZE, типы сканов, почему индекс не используется | Задания 2, 3, 4 |
| Пагинация: OFFSET vs keyset                                 | Задание 3       |
| N+1, JOIN, оконные функции, LATERAL                         | Задание 4       |
| ACID, уровни изоляции, аномалии, блокировки, дедлоки        | Задание 5       |
| Идемпотентность, уникальные ограничения, ON CONFLICT        | Задание 6       |
| Кэш, инвалидация, rate limit (Redis)                        | Задание 7       |
| FastAPI: lifespan, Depends с yield, слои, тесты             | Сквозное        |

## Стек и архитектура

Стек держим минимальным: каждая зависимость нужна для конкретного вопроса собеса, а не для красоты.

| Что         | Выбор                                   | Зачем                                        |
| ----------- | --------------------------------------- | -------------------------------------------- |
| Язык        | Python 3.12+                            | актуальный синтаксис, `TaskGroup`            |
| Фреймворк   | FastAPI + Pydantic v2                   | твой основной стек                           |
| Настройки   | pydantic-settings + `.env`              | конфиг из переменных окружения               |
| БД          | PostgreSQL 17 в Docker                  | целевая БД вакансии                          |
| Драйвер     | asyncpg, без ORM                        | сырой SQL, пул соединений, транзакции руками |
| Миграции    | пронумерованные `.sql` + скрипт накатки | понять, как устроены миграции без магии      |
| Кэш         | Redis 7 + `redis.asyncio`               | только задание 7                             |
| Тесты       | pytest + pytest-asyncio + httpx         | тест на гонку в задании 5                    |
| Зависимости | uv                                      | lock-файл, быстрый venv                      |
| Инфра       | docker compose: api, postgres, redis    | поднять всё одной командой                   |

**Архитектура: три слоя, без Clean Architecture на полную.** Роутер принимает HTTP и валидирует вход. Сервис держит бизнес-логику и **границы транзакций**. Репозиторий содержит только SQL и принимает соединение аргументом, поэтому несколько вызовов репозитория живут в одной транзакции. Соединение и Redis-клиент приходят через `Depends`, пул создаётся в `lifespan`.

&#91;embedded content: слои приложения · роутер, сервис, репозиторий\]

Запрос идёт слева направо. Сервис открывает `conn.transaction()` и вызывает несколько методов репозитория с одним и тем же соединением.

**Redis: да, но последним и в узком объёме.** В вакансии акцент на PostgreSQL, а собес в понедельник, так что Redis не должен отнимать время у заданий 2–5. Но вопросы про кэш, TTL, инвалидацию и rate limit задают почти на любом бэкенд-собесе, а для сервиса с LLM rate limit особенно уместен. Поэтому Redis поднимаем в compose сразу, а используем только в задании 7.

## Структура проекта и схема БД

```
llm-chat/
├── app/
│   ├── main.py            # FastAPI(), lifespan, подключение роутеров
│   ├── config.py          # Settings через pydantic-settings
│   ├── deps.py            # get_conn(), get_redis()
│   ├── api/               # роутеры: users.py, chats.py, transfers.py
│   ├── services/          # бизнес-логика и транзакции
│   ├── repositories/      # только SQL
│   └── schemas/           # Pydantic-модели запросов и ответов
├── migrations/            # 001_init.sql, 002_indexes.sql, ...
├── scripts/
│   ├── migrate.py         # накатывает неприменённые .sql
│   ├── seed.sql           # генерация данных
│   └── race.py            # параллельные запросы для задания 5
├── reports/               # отчёты по заданиям (см. «Что прислать»)
├── tests/
├── docker-compose.yml
└── pyproject.toml
```

Таблицы. Индексы здесь намеренно не указаны: в `001_init.sql` только PK, FK и ограничения, а индексы ты добавляешь сам в задании 2.

| Таблица     | Колонки                                                 | Ограничения                          |
| ----------- | ------------------------------------------------------- | ------------------------------------ |
| `users`     | id, email, balance, created_at                          | email UNIQUE, `CHECK (balance >= 0)` |
| `chats`     | id, user_id, title, created_at                          | FK → users                           |
| `messages`  | id, chat_id, role, content, idempotency_key, created_at | FK → chats, role ∈ user/assistant    |
| `transfers` | id, from_user_id, to_user_id, amount, created_at        | `CHECK (amount > 0)`, from ≠ to      |

Подумай сам: нужен ли индекс на FK, и создаёт ли его Postgres автоматически. Это частый вопрос с подвохом.

## Задания

У каждого задания есть критерии готовности и вопросы. Ответы пиши своими словами в отчёт задания: именно они превращают практику в готовые ответы на собесе.

### 1. Сетап и данные

1. `docker compose up` поднимает api, postgres и redis.
2. Пул asyncpg создаётся в `lifespan`, `get_conn()` отдаёт соединение через `yield`.
3. `scripts/migrate.py` ведёт таблицу `schema_migrations` и накатывает только новые файлы, каждый в своей транзакции.
4. `seed.sql` через `generate_series`: 10 тыс. юзеров, 100 тыс. чатов, 3 млн сообщений. Распредели сообщения неравномерно: пусть несколько чатов будут очень большими.
5. После сида выполни `ANALYZE`.

Готово, когда проект с нуля поднимается тремя командами из README. **Вопросы:** зачем нужен пул соединений? Что делает `ANALYZE` и почему без него планы бывают плохими?

### 2. Индексы и EXPLAIN

1. `GET /chats/{chat_id}/messages?limit=50` — последние сообщения чата, новые сверху. Сначала без индекса, потом попробуй `(chat_id)`, `(created_at)` и `(chat_id, created_at DESC)` по очереди.
2. `GET /users/by-email?email=...` без учёта регистра. Покажи, что обычный индекс не работает с `lower(email)`, и почини функциональным индексом.
3. Покажи, что `WHERE content LIKE '%hello%'` не использует B-tree. Бонус: почини через GIN + `pg_trgm`.
4. Частичный индекс: поиск только по сообщениям `role = 'user'`.
5. Найди запрос, где Postgres сам выбирает Seq Scan, хотя индекс есть (подсказка: плохая селективность).
6. Сравни время вставки 100 тыс. сообщений без индексов и со всеми индексами.

Готово, когда для каждого пункта есть `EXPLAIN (ANALYZE, BUFFERS)` до и после. **Вопросы:** как устроен B-tree? В чём разница Seq, Index, Index Only и Bitmap Scan? Почему в составном индексе важен порядок колонок? Чем индексы вредят?

### 3. Пагинация

1. Версия с `?offset=&limit=`.
2. Keyset-версия с курсором `(created_at, id)`: сравнение кортежей `WHERE (created_at, id) < ($1, $2)`. Подумай, зачем в курсоре `id`.
3. Сравни обе версии на offset 0, 10 тыс. и 100 тыс. в самом большом чате.

Готово, когда есть таблица времён. **Вопрос:** почему OFFSET медленный и какие минусы у keyset?

### 4. N+1 и JOIN-ы

1. `GET /users/{id}/chats` — чаты юзера и в каждом последние 3 сообщения. Сначала наивно: запрос в цикле. Посчитай запросы и время.
2. Одним запросом через `ROW_NUMBER() OVER (PARTITION BY ...)`.
3. Одним запросом через `LEFT JOIN LATERAL (... LIMIT 3)`.
4. Бонус: собери сообщения в JSON через `json_agg`.
5. `GET /stats/top-users` — топ-10 юзеров по числу сообщений за 7 дней с `GROUP BY` и `HAVING`.

Готово, когда есть сравнение трёх вариантов по числу запросов, времени и плану. **Вопросы:** что такое N+1 и почему это проблема? В чём разница INNER, LEFT и LATERAL JOIN? Чем WHERE отличается от HAVING? Какие есть стратегии JOIN в плане (Nested Loop, Hash, Merge)?

### 5. Транзакции и гонки (главное)

1. `POST /transfers {from_user_id, to_user_id, amount}` — наивная версия: SELECT баланса, проверка в Python, два UPDATE и INSERT в `transfers`. Убери `CHECK (balance >= 0)` на время этого пункта, иначе БД спрячет баг.
2. `scripts/race.py`: 50 параллельных переводов по 100 с счёта с балансом 1000 через `asyncio.gather` + `httpx`. Докажи гонку: успешных переводов больше 10 или сумма балансов изменилась.
3. Почини тремя способами, каждый в отдельной функции сервиса:
   1. `SELECT ... FOR UPDATE`
   2. атомарный `UPDATE ... SET balance = balance - $1 WHERE id = $2 AND balance >= $1` + проверка числа затронутых строк
   3. `SERIALIZABLE` + ретрай на `SerializationError` через твой декоратор `@retry`
4. Верни `CHECK (balance >= 0)` и объясни, почему ограничение в БД должно быть всегда, даже при правильном коде.
5. Дедлок: одновременные переводы A→B и B→A. Поймай `DeadlockDetectedError`, потом устрани его блокировкой строк в порядке возрастания id.
6. Исключение после первого UPDATE должно откатывать всё. Напиши на это тест.
7. В двух окнах `psql` воспроизведи non-repeatable read на Read Committed и покажи, что на Repeatable Read его нет.

Готово, когда `race.py` до фикса ломает данные, а после каждого из трёх фиксов даёт ровно 10 успехов и неизменную сумму балансов. **Вопросы:** что такое ACID? Какие уровни изоляции и аномалии существуют, и какой уровень в Postgres по умолчанию? Что такое MVCC? Пессимистичная или оптимистичная блокировка — что и когда? Как возникает и как предотвращается дедлок?

### 6. Идемпотентность

1. `POST /chats/{id}/messages` с заголовком `Idempotency-Key`. Уникальный индекс по `(chat_id, idempotency_key)` + `INSERT ... ON CONFLICT DO NOTHING RETURNING`.
2. Повторный запрос с тем же ключом возвращает уже созданное сообщение, а не создаёт дубль. Проверь это 20 параллельными запросами.

**Вопрос:** почему проверка «сначала SELECT, потом INSERT» здесь не работает?

### 7. Redis (после всего остального)

1. **Rate limit:** не больше 10 сообщений в минуту на юзера через `INCR` + `EXPIRE` (fixed window), оформлено как зависимость FastAPI. При превышении — `429`.
2. **Кэш:** кэшируй `GET /stats/top-users` на 60 секунд по паттерну cache-aside. Измерь время с кэшем и без.

**Вопросы:** какие есть стратегии кэширования и инвалидации? Что такое cache stampede? Почему fixed window неточен и что точнее (sliding window, token bucket)?

## Что прислать на проверку

Присылай по одному заданию, не всё сразу: так ошибки не успеют переехать в следующие задания. Ссылка на GitHub или файлы архивом в чат, плюс отчёт `reports/NN-<тема>.md`.

Каждый отчёт содержит:

1. **SQL** каждого запроса и миграции.
2. **Планы `EXPLAIN (ANALYZE, BUFFERS)`** до и после, целиком, без обрезки.
3. **Таблица цифр:** вариант, тип скана, время, число запросов.
4. **Вывод `race.py`** до и после фикса (для заданий 5 и 6).
5. **Ответы на вопросы задания** своими словами, как будешь говорить на собесе, 3–5 предложений на вопрос.
6. **Что удивило или не понял:** 1–2 строки. Это самая ценная часть для разбора.

Как я проверяю: как на код-ревью (корректность, транзакции, SQL-инъекции, обработка ошибок), потом разбираю планы, потом задаю 2–3 уточняющих вопроса по твоим ответам, как интервьюер.
